# 微信 4.x 本地图片解密：从「打不开」到全库 7216 张可用

## 一句话经验

> 图片解密失败先别怀疑算法，先确认 `uin=0` 这类**合法零值**有没有被 `if uin:` 当成「没取到」；解密后先打印文件头字节再交给 Pillow，能省掉一整轮瞎猜。

## 一、这次要交付什么

让本机微信 4.x 聊天里的图片能被稳定导出成可打开的原图，供材料台账、摘录成文、公众号配图使用。

验收标准：随便挑一张聊天图片，能导出、能用看图软件打开、分辨率与原始一致；全库批量跑不报错。

明确不在范围内：通过 UI 自动化**发送**微信消息（本机微信只在托盘、没有主窗口，`mmui::MainWindow` 找不到，这条路未经证实，不做）。

## 二、用到的材料

| 材料 | 路径 / 来源 | 说明 |
| --- | --- | --- |
| 微信本地数据库与图片文件 | `xwechat_files` 账号目录下 | 4.x 的存储结构与 3.x 不同 |
| 账号 uin / 密钥派生参数 | 本机配置与数据库 | 派生 AES+XOR 密钥的输入 |
| 图片消息引用 | 消息里的 `media_ref`（32 位 hex） | 单图定位用 |
| ffmpeg | 本机可选 | WXGF 格式转 PNG 时才需要 |

## 三、完整流程（照着做）

1. 先跑 `work_wechat_probe`，确认 `wechat_version`、账号目录、UI 自动化状态；微信 4.x 不指望 UIA，直接走本地库只读通道。
2. 用 `work_wechat_sessions` / `work_wechat_messages` 找到目标消息，取 `media_ref` 与发送时间。
3. 调 `work_wechat_media`：单图用 `ref=<32位hex>` + `prefer=orig`；批量用 `limit` 控制数量，先小范围试。
4. 解密后**先看文件头字节**（PNG 是 `89 50 4E 47`，JPG 是 `FF D8 FF`），再交给 Pillow 打开。
5. 产物落 `workspace/09_微信图片/`，再按需嵌进 `work_wechat_digest` 的成文稿或公众号配图。
6. 网页灯箱里点缩略图时，用同一个 `ref` 重新请求 `prefer=orig`，自动换成原图（缩略图只有 210px，直接放大会糊）。

## 四、关键口径与决策

- **不覆盖、不写回微信库**：全程只读本地文件，解密产物另存到工作区，避免污染原始聊天数据。
- **缩略图优先、原图按需**：列表用 `thumb`（快，且不需要 ffmpeg），只有点开或明确要原图时才 `prefer=orig`。
- **宁可明确报不可用，也不假装能力存在**：UIA 发送这条路没验证成功，就在能力清单里标为边界，不写进对外功能。
- 灯箱竖图用 `calc(100vh - 80px)` 约束高度：`max-height:100%` 在 grid 轨道里会失效，竖图会冲出屏幕。

## 五、踩过的坑（别再犯）

- **现象**：Pillow 报「无法识别图像」，但解密流程没抛异常，头几轮一直怀疑 AES/XOR 算法或文件格式。
  **根因**：`uin=0` 是合法值，代码里用 `if uin:` 判空，0 被当成「没取到」，于是走了另一条派生路径，密钥错了，解出来的是乱码字节。
  **改法**：改成 `if uin is None`；并在 `to_image` 里把解密结果的前几个字节一起报出来，一眼能分清「算法错」还是「格式没转」。
  **结果**：修完后全库 7216 张图片可导出，原图 1280×1706 PNG 正常打开。
- **现象**：本地 curl 访问 127.0.0.1 恒返回 502。
  **根因**：环境里设了 `http_proxy`，本机回环请求也被送进代理。
  **改法**：`curl --noproxy 127.0.0.1,localhost ...`，或在命令前设 `NO_PROXY=127.0.0.1,localhost`。
- **现象**：受管后台起的服务，会话结束时被回收，页面忽然打不开。
  **改法**：用受管的后台任务方式启动，别用 `&` / `nohup` 之类的脱离方式。
