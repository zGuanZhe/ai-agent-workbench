# 企业微信：和微信同一套动作，另一套通道

> 归属**通讯模块**（同上）；企业微信与微信是两条独立通道，别混用工具前缀。

## 跨通道「最近有什么通知」先走聚合（第一选择）

「通讯软件里有什么值得注意的通知」「最近有什么消息」这类**没有点名通道**的泛问，
不要从本文的单通道工具开始逐个群读：先调一次 `work_comms_notices`（默认最近 3 天，
同时扫微信与企业微信，通知排在闲聊前面、带 `due` 的更靠前）。
完整口径见 `references/wechat.md` 首节。本文下面的工具只在**点名企业微信**、
要读某条全文、搜历史某句话、收文件时才用。

聚合结果里 `channel="企微"` 的行来自本通道；若 `channels` 里企微是 `ready=false`，
要如实说明「客户端没开 / 密钥取不到」，不能拿微信那一侧的数据凑数。

## 先看通道

`work_wecom_probe` 一次说清能不能读：

| 字段 | 含义 | 为 false 时 |
| --- | --- | --- |
| `running` | `WXWork.exe` 在不在跑 | 取不到密钥，读不了；先让用户把客户端打开并保持登录 |
| `cached_key` | 密钥缓存有没有 | 有缓存时客户端关着也能读**已解密过**的那部分 |
| `db_encrypted` / `db_plain` | 加密库与明文库各几个 | 全部 `db_plain` 说明这台机器没开加密，直接读 |
| `cache_dir` | 解密副本落在哪 | 副本可以随便删，下次自动重建 |

**为什么必须开着客户端**：企业微信用 wxSQLite3 加密，密钥只在 `WXWork.exe` 的进程内存里，
不落盘、不在配置文件里。客户端关了，谁都解不开——这不是工具坏了，是这条路的前提。

换账号、升级客户端后第一次会重扫内存（20–30 秒），之后走指纹缓存，秒级。

## 读什么

| 要做的事 | 工具 | 关键参数 |
| --- | --- | --- |
| 列会话 | `work_wecom_sessions` | `limit`、`only_unread` |
| 看某个群/人最近的消息 | `work_wecom_messages` | `chat` 必填（群名 / 片段 / `R:` id） |
| 谁提过某件事 | `work_wecom_search` | `keyword` 必填；`since` 给窄一点更快 |
| 查人 | `work_wecom_contacts` | `keyword` 可空，空则按 `limit` 列全部 |
| 收到过哪些文件 | `work_wecom_files` | `since` / `exts` |
| 密钥或缓存不对 | `work_wecom_sync` | `force=true` 丢掉密钥缓存重扫 |

搜消息是**在内存里逐条解正文再匹配**：正文是 protobuf，SQL 的 `LIKE` 搜不到。
所以先 `since` 压范围，再搜。

## 收材料

`work_wecom_harvest`：按时间窗 / 群 / 扩展名筛出收到的文件，复制到
`workspace/01_企业微信收回原件`，可加 `{chat}` / `{sender}` 前缀，按内容去重。

**`dry_run` 默认 true**，只给计划不落盘。用户说「收」也先跑一次 dry-run 报数，
确认了再 `dry_run=false`。

### 结果怎么读

| 字段 | 含义 |
| --- | --- |
| `copied` | 本次新复制几份 |
| `skipped_duplicate` | 之前收过、按内容跳过（**不是失败**） |
| `not_downloaded` | 云端有、本地没有的文件，收不到 |

`on_disk=false` 很常见：企业微信的云端文件要在客户端点开才落地。这是真实状态，
不是没找到——不要为了凑数把 `not_downloaded` 当成已收报给用户。

## 和微信分清楚

两套完全不同的加密，别混着说、也别混着调：

| | 微信 | 企业微信 |
| --- | --- | --- |
| 加密 | SQLCipher，逐页 HMAC 校验 | wxSQLite3，AES-CBC 逐页、无 HMAC |
| 密钥来源 | `Config.Cipher` 里的 XOR 掩码 | `WXWork.exe` 进程内存 |
| 客户端关着 | 有缓存就能读 | 没密钥就读不了 |
| 工具前缀 | `work_wechat_*` | `work_wecom_*` |

用户说「企业微信 / 企微 / WXWork」才走 `work_wecom_*`；只说「微信」不要自己升级成企业微信。
反过来，用户明确说企业微信却调了 `work_wechat_*`，会读到一个空收件箱——比报错更难发现。

## 不要承诺的

- **不发消息**：企业微信这边只读，不假装 @ 人、不假装发群通知。
- **不解图片和语音**：`work_wecom_files` 只给文件名与元信息；媒体本体还在客户端缓存里。
- **不做全库 FTS**：几个 FTS 索引库用私有 tokenizer，解出来也打不开，不影响会话/消息/文件三件事。

## 通讯总览：一个入口看两条通道

控制台把「微信」「企业微信」两列合并成一列 **通讯**；同名能力成对出现，节点右侧带
「微信 / 企微」徽标。顶部第一个节点是 **通讯总览**。

- 工具：`work_comms_overview(limit=6)`；意图：`comms_overview`；接口：`/api/comms/overview`。
- 一次返回两条通道的 `ready / status / hint / metrics / sessions`，外加 `recent`——
  两边会话按时间合成的一条时间线，每行带 `channel`（微信 / 企微）。
- 某条通道读不了时，总览本身仍然 `ok:true`，那张卡变灰并写清原因；**不要因为一边
  不通就说整个通讯坏了**，也不要把企微「客户端没开、密钥取不到」讲成「没有数据」。
- 它是**状态 + 最近会话的合视图，不是统一搜索、也不是统一收件**，更**不含消息正文**。
  问「最近有什么通知」用 `work_comms_notices`，别拿总览的会话摘要硬答。
  用户要搜某句话、收某个群的文件，仍按有没有「企业微信 / 企微 / WXWork」分别走
  `work_wechat_search` / `work_wecom_search`、`work_wechat_files(mode='harvest')` / `work_wecom_harvest`。
- 「通讯录」不等于「通讯总览」：说「企微通讯录里查一下王」要命中 `work_wecom_contacts`，
  路由里已加互斥用例，别让泛称把专有动作抢走。
